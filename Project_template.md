# Задание 1. Исследование моделей и инфраструктуры

## 1. Сравнение LLM-моделей: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

| Критерий                     | Локальные модели (Hugging Face)                                                                 | Облачные модели (OpenAI / YandexGPT)                                             |
|------------------------------|--------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| **Качество ответов**         | Среднее–высокое. Современные open-weight модели (Mistral 7B, Llama 3 8B) приближаются к GPT-3.5. | GPT-4 Turbo — наилучшее качество; YandexGPT 2.0 — конкурентоспособен для русскоязычного контекста. |
| **Скорость работы**          | Зависит от инфраструктуры: без GPU — медленно (до нескольких секунд на токен).                   | Высокая и стабильная (1–2 сек/запрос), но зависит от сетевой задержки.           |
| **Стоимость владения**       | Высокие капитальные затраты на GPU/сервер, но нулевые операционные расходы при высокой нагрузке. | Операционная модель: $0.01–$0.1/запрос. При 100+ запросах в день — затратно.     |
| **Удобство развёртывания**   | Требует DevOps, ML-инжиниринга, настройки инференса и мониторинга.                               | Простая интеграция через REST API, готово к использованию «из коробки».          |
| **Конфиденциальность данных**| Полный контроль. Данные не покидают периметр компании.                                          | Риск утечки: данные передаются третьим лицам (нарушение требований SOC 2).      |

**Вывод**:  
Для QuantumForge, где часть документации содержит промышленные спецификации и данные клиентов (ABB, Wärtsilä), **локальные LLM предпочтительны для основной массы запросов**. Облачные модели допустимы **только для нетипичных, неконфиденциальных задач** (например, генерация onboarding-инструкций по публичным темам).

## 2. Сравнение моделей эмбеддингов: Sentence-Transformers vs OpenAI Embeddings

| Критерий                     | Sentence-Transformers (локально)                                                               | OpenAI Embeddings (облако)                                                     |
|------------------------------|--------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| **Скорость индексации**      | Линейно зависит от CPU/GPU. На современном CPU — 10–50 мс/документ.                              | Быстро, но лимитировано API (до 3000 req/min у OpenAI).                        |
| **Качество поиска**          | Высокое для английского и технического текста (e.g., `all-mpnet-base-v2`, `e5-base-v2`).        | Лучшее в отрасли (особенно `text-embedding-3-large`), но избыточно для внутренней базы. |
| **Стоимость**                | Нулевая после развёртывания.                                                                     | $0.13/1M токенов (OpenAI). При 18k документов — небольшая, но регулярная статья расходов. |
| **Конфиденциальность**       | Данные остаются внутри компании.                                                                | Документы передаются в облако — **неприемлемо** для SOC 2 и клиентских NDA.     |

**Вывод**:  
**Использовать локальные эмбеддинги** (например, `BAAI/bge-base-en-v1.5` или `intfloat/e5-base-v2`). Они обеспечивают отличное качество поиска по технической документации и полностью соответствуют требованиям безопасности.

## 3. Сравнение векторных баз: FAISS vs ChromaDB

| Критерий                     | FAISS (Meta)                                                                                   | ChromaDB                                                                 |
|------------------------------|--------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| **Скорость поиска**          | **Выше**: 1–10 мс на 100k векторов благодаря оптимизированному C++ ядру.                        | 10–50 мс (накладные расходы на Python-обёртки и сервер).                |
| **Индексация**               | Требует полной перезаписи при обновлении. Не поддерживает потоковую вставку «из коробки».       | Поддерживает динамическое добавление и удаление документов.             |
| **Управление метаданными**   | Нет встроенной поддержки. Требуется внешняя база (PostgreSQL) для хранения источников, типов и т.д. | **Встроенная поддержка метаданных**, фильтрации по источнику (Confluence, PDF, GitHub). |
| **Удобство разработки**      | Прост для PoC, но требует дополнительного кода для продакшена.                                  | Единый API, встроенный HTTP-сервер, интеграция с LangChain «из коробки». |
| **Стоимость и поддержка**    | Бесплатно. Минимальные требования к железу.                                                    | Бесплатно, но потребляет больше памяти (из-за сервера и метаданных).    |

**Вывод**:  
Несмотря на более высокую скорость, **FAISS неудобен для динамической базы знаний** с ежемесячным приростом 400+ документов. **ChromaDB лучше подходит** для QuantumForge: он поддерживает обновление контента, фильтрацию по типу документа (например, «только Confluence» или «только SCADA-интеграции») и упрощает аудит.

## 4. Рекомендуемая серверная конфигурация

Для стабильной работы RAG-бота с объёмом ~21 000 документов и 100+ активных пользователей:

| Компонент       | Рекомендация                         | Обоснование                                                                 |
|------------------|--------------------------------------|-----------------------------------------------------------------------------|
| **CPU**          | 8–16 ядер (AMD EPYC / Intel Xeon)    | Обработка эмбеддингов и параллельных запросов.                              |
| **RAM**          | 32–64 ГБ                             | ChromaDB + индекс ~5–8 ГБ + буфер для запросов.                             |
| **GPU**          | **Опционально**: NVIDIA T4 или L4    | Ускорение генерации локальной LLM (например, Mistral 7B). Без GPU — CPU-only инференс. |
| **Storage**      | 1 ТБ NVMe SSD                        | Хранение исходных документов, индексов и логов.                             |
| **Сеть**         | 1 Гбит/с, низкая задержка            | Для интеграции с внутренними сервисами (Confluence API, GitHub, S3).        |

> **Примечание**: При использовании локальной LLM GPU **обязателен**. При отказе от LLM (только retrieval + правило-генерация) — достаточно CPU.

## Сравнение архитектурных вариантов

| Параметр                | Вариант A: Локальный стек          | Вариант B: Гибридный                             | Вариант C: Полностью облачный                |
|-------------------------|------------------------------------|--------------------------------------------------|----------------------------------------------|
| **LLM**                 | Mistral 7B или Llama 3 8B (локально) | Локальный для конфид. + GPT-3.5 для общих тем    | GPT-4 Turbo                                   |
| **Эмбеддинги**          | `BAAI/bge-base-en-v1.5` (локально) | То же                                            | `text-embedding-3-small`                      |
| **Векторная БД**        | ChromaDB                           | ChromaDB                                         | Pinecone / Weaviate                           |
| **Инфраструктура**      | Own server или AWS EC2 (g5.xlarge) | AWS EKS + On-prem ChromaDB                       | Fully managed cloud (OpenAI + Pinecone)       |
| **Конфиденциальность**  | Полный контроль                    | Частичная (облако — только для публичных тем)    | Риск утечки                                |
| **Стоимость (мес.)**    | ~$0 (после CapEx)                  | ~$600–$900 (облако + хостинг)                    | ~$2000+                                       |
| **Масштабируемость**    | Требует DevOps                     | Высокая                                          | Максимальная                                  |
| **SOC 2 совместимость** | Полностью                          | Требует строгой сегрегации запросов              | Не проходит аудит                          |

## Итоговая рекомендация

**Выбираем Вариант A (локальный стек)** с возможностью **ограниченного гибридного расширения в будущем**.

**Обоснование**:
- QuantumForge работает с **чувствительными данными промышленных клиентов**, что делает **локальное хранение и обработку обязательным**.
- ChromaDB обеспечивает **гибкость обновления** и **фильтрацию по источникам** — критично при разрозненной документации.
- Локальные эмбеддинги и LLM **соответствуют требованиям SOC 2** и исключают риски передачи данных.
- Хотя первоначальные затраты выше ($8k–$12k на сервер), **срок окупаемости < 6 месяцев** за счёт экономии FTE и сокращения 140 часов на аудит.
- Архитектура **масштабируема**: в будущем можно добавить кэширование (Redis), мониторинг (Prometheus), и даже клиентский RAG-модуль как часть SaaS-платформы.

> Таким образом, **ChromaDB + локальные эмбеддинги + open-weight LLM** — оптимальный баланс безопасности, стоимости и функциональности для QuantumForge Software.
